# Project Structure and Stale-Code Audit

Audit date: 2026-10-09
Scope: read-only review of the Omaxe Daily Tracker repository, including tracked Markdown, application source, Firebase configuration, dependencies, tests, and local release/build artifacts.
Authorization boundary: do not modify application code, financial data, Firebase configuration, Rules, dependencies, Git history, or deployment state without a separate request. This file is the only intended source-workspace change from this audit. Build output and emulator logs may be regenerated by the requested validation drill.

## Executive summary

The app is not showing evidence of a broad pile of safely deletable source files. The more valuable cleanup is to make the current architecture and docs agree, reduce a few confirmed repetitions, and split a handful of large mixed-responsibility files in small, tested steps.

The highest-priority findings are:

1. **Tracked operational data needs an exposure/retention decision.** The repository tracks backup and stock data under `docs/backups/` and `data/pos/`, plus `server/omaxe.db`. A prior archived audit reported that the GitHub repository was publicly readable and that the backup files contain personal/financial data. Current repository visibility was not verified in this audit. Do not delete or rewrite history as a cleanup shortcut; first establish current access and the approved retention/containment path.
2. **Current documentation is behind the released product.** The latest source/release commits are dated 2026-10-09, but key current docs were last updated on 2026-10-04 or earlier. The README omits the live POS/GRN/stock-audit experience, and the roadmap still says inventory is outside scope even though GRN and stock audit are in the deployed code.
3. **There are confirmed exact helper duplications.** `normalizeName` and `uniqNames` have matching implementations in `src/app/uiHelpers.ts` and `src/store/storeShared.ts`. Consolidation is a good small cleanup after a focused behavior test.
4. **A few modules have become broad workflow containers.** The POS repository, POS page/GRN page, Vendor Workspace, Finance action factory, and `AppWorkspace` are the strongest candidates for gradual boundary-based extraction—not wholesale rewrites.
5. **The production build warns about a large entry chunk.** The current build emits a 1,395.32 kB JavaScript chunk (412.24 kB gzip), above Vite’s 500 kB warning threshold. Route/feature-level splitting is worth evaluating after correctness and boundaries are covered.
6. **Dependency audits have unresolved advisories.** The root application audit reports 3 vulnerabilities (2 high, 1 critical); the Functions audit reports 9 moderate. These are transitive dependency findings and do not by themselves prove exploitability in the browser bundle. Do not run `npm audit fix` blindly; assess actual runtime reachability and use controlled upgrades.

Validation is currently healthy: ESLint on `src tests` passed, 109 unit tests passed, 61 Firestore Rules emulator tests passed against the demo project, and the production build passed. No Firebase production reads/writes, deployment, or financial mutations were performed for this audit.

## Findings

### P0 — Tracked business/backup data and repository exposure (status requires owner verification)

Tracked paths include:

- `docs/backups/*.json` (three backup files)
- `data/pos/omaxe-opening-stock-2026-10-02.approved.csv`
- `data/pos/omaxe-opening-stock-2026-10-02.evidence.json`
- `server/omaxe.db`

The audit read only path names and repository history notes, not the contents of these records. The archived 2026-10-01 cleanup audit records the repository as publicly readable at that time and says the tracked backups contain personal and financial information; it also says the owner chose report-only handling. That is historical evidence, not confirmation of current repository visibility.

**Recommendation:** verify current repository access and backup ownership/retention as a separate security decision. If exposure remains, choose containment with the owner before moving/removing files or rewriting Git history. Preserve a recoverable, access-controlled copy before any approved remediation. Do not fold this into routine source cleanup.

### P1 — README and roadmap no longer describe current product scope

- `README.md` describes the current app but its feature and navigation lists omit POS, Billing, Bills, Goods Receipt, and Stock Audit. The current workspace has a POS page and the latest Oct 9 release includes POS, GRN, and audit work.
- `docs/operations/ROADMAP.md` line 40 lists inventory as outside the approved scope, while current POS code includes goods receipt and multi-item stock audit workflows (`src/features/pos/components/PosGoodsReceipt.tsx`, `src/features/pos/data/posRepository.ts`). The roadmap also needs reconciliation with the current vendor/GRN workflow.
- `docs/operations/VERSION_LOG.md` has no Oct 4 or Oct 9 release entries; its latest section is the Oct 1 cleanup candidate. It therefore does not provide a current release history for the latest shipped changes.
- `docs/operations/POS_CHECKOUT_IMPROVEMENTS.md` says deployment of the checkout update is unconfirmed, although the later Oct 9 combined POS release commit is present. Update the status to point to the combined release rather than leaving the earlier uncertainty as the latest signal.
- `docs/architecture/ARCHITECTURE_AUDIT_2026-10-03.md` is a useful dated snapshot, not a current architecture guide. Its historical assertions must not be copied forward without rechecking against current source.

**Recommendation:** update the current README, Architecture, Roadmap, QA checklist, and Version Log from the current code and actual release evidence. Preserve dated checkpoints and audit reports as historical records; label old snapshots clearly rather than rewriting their conclusions silently. Add a compact “last verified against commit/date” note to the canonical docs.

### P1 — Local release snapshots are highly repetitive, but not yet safe to remove

`output/` contains three dated release trees, a QA tree, and an empty `pos-import` directory. The three release trees are each about 4.9–5.1 MB; `pos-qa` is about 19.9 MB. Among the 48 Markdown copies outside dependency folders, hash comparison found 15 relative paths present identically in all three release trees and one relative path copied in two trees; one additional checkout-improvement note is unique to a snapshot. These repeated docs include canonical README, architecture, domain, operations, setup, archive, and POS README files.

The snapshots are untracked and may have been retained as release evidence or backups. Duplicate Markdown alone does not prove each whole snapshot is disposable.

**Recommendation:** after verifying each snapshot against its release commit/tag and checking for unique user evidence, keep one documented archival representation (prefer Git history plus compact QA/release reports) and remove redundant full-tree copies only with explicit approval. Do not delete `output/`, `output/pos-qa`, the empty folder, or any release/back-up data in this audit.

### P2 — `normalizeName` and `uniqNames` are duplicated exactly

`src/app/uiHelpers.ts` and `src/store/storeShared.ts` each define the same `normalizeName` whitespace-trimming helper and `uniqNames` de-duplication/sorting helper. UI and store/action code use these helpers across different feature areas.

**Recommendation:** in a small approved change, create one neutral shared utility module (for example, `src/shared/lib/nameUtils.ts`), update both import families, and add/retain tests for whitespace normalization, case-insensitive uniqueness, stable display casing, and sorting. Avoid making UI helpers depend on the store or vice versa.

### P2 — Duplicated calculations should be reviewed, not blindly merged

- Monthly dashboard performance is derived in `src/features/dashboard/domain/deriveMonthlyPerformance.ts`; the shared snapshot is derived in `src/store/deriveWorkspaceMetrics.ts`. They overlap in sales, payment mix, and day summaries but serve different outputs and historical semantics. Treat this as a consistency review, not confirmed duplicate code.
- `src/store/actions/createFinanceActions.ts` contains daily-sales synchronization/reconstruction alongside finance actions. Compare its batched and non-batched/rebuild paths before consolidation; do not alter cashout/sales atomicity or historical totals as part of a cleanup.
- Currency formatting is centralized in `money()` in `src/app/uiHelpers.ts`, but some vendor screens format paise inline. Consider a shared formatter only after defining output rules for INR, paise, decimals, and negative values.

**Recommendation:** make a calculation inventory with source-of-truth outputs and regression examples first. Never merge financial calculations on visual similarity alone.

### P2 — Large first-load bundle

The production build succeeds but emits a 1,395.32 kB JavaScript chunk (412.24 kB gzip), with Vite’s warning above the 500 kB threshold.

**Recommendation:** inspect bundle composition and route/feature imports, then consider code-splitting large owner-only areas and POS workflows. Verify at 75% and 100% zoom, keyboard/scanner workflows, and cold-load behavior. Avoid manual chunk rules until the bundle report shows a real split point.

### P2 — Dependency advisories require a controlled security pass

Audit commands on 2026-10-09:

- Root `npm audit --omit=dev`: 3 vulnerabilities (2 high, 1 critical): `@grpc/grpc-js`, `protobufjs`, and `websocket-driver` in transitive Firebase SDK dependency paths.
- `npm audit --omit=dev --prefix functions`: 9 moderate vulnerabilities through `uuid` and Google/Firebase Admin/Functions dependencies. The suggested forced remediation requires a breaking `firebase-functions` major update.
- `npm ls --depth=0` succeeds for root and Functions; no invalid or missing top-level package was reported.

These audit results establish package-tree advisories, not that each vulnerable module is shipped/executable in the browser or exploitable in the deployed Functions runtime. `npm audit fix` and forced upgrades were not run.

**Recommendation:** review reachability in the built browser bundle and deployed Functions runtime; then upgrade the smallest compatible dependency sets in an isolated branch with unit/Rules/build checks and a separate Functions deployment decision.

### P3 — Documentation structure is sizable but has a reasonable archive split

The archive contains three intentional historical records. Dated phase checkpoints should remain historical evidence; the main opportunity is clarifying which docs are current/canonical, not deleting them to reduce the count.

**Recommendation:** designate a short canonical set (`README.md`, `docs/architecture/ARCHITECTURE.md`, `docs/domain/*`, `docs/operations/ROADMAP.md`, `QA_CHECKLIST.md`, `RELEASE_PROCESS.md`, `ROLLBACK.md`, and `VERSION_LOG.md`). Keep design references and approved/historical decision records in their current specialized locations. Add an index or “current vs historical” note rather than consolidating every Markdown file again.
