## Required environment before any manual mutation

Current drill URLs bind loopback and the client hardcodes loopback emulator endpoints. A phone's `127.0.0.1` refers to the phone, so these URLs cannot be used as a real-device setup. No phone/device session was connected during maintenance. Do not substitute the production site or `posSandboxes/test` in production.

A separately reviewed device-access configuration must provide: synthetic project identity; reachable isolated Auth/Firestore/Functions endpoints; HTTPS for native install where required; matching client config, endpoint assertions/outbound controls, network access restriction and a documented reset owner. Verify every actual device's SDK project/hosts and observed requests before login/posting. The existing strict loopback guards must not simply be disabled to make access work. Record exact hosts/project, app asset version, browser/OS/device, role and evidence. Do not expose emulators to an untrusted network or use real credentials/Telegram recipients.

After that setup is available, finish automated runs, close all browser contexts, seed the synthetic environment once through its approved guard, then assign A/B/owner physical sessions. Never reset while a scenario/device is using fixtures. Use unique operation IDs and read persisted records independently from a trusted observer. Stop on any production hostname/project, real data, wrong date, loan record, missing endpoint proof or unexpected external send.
