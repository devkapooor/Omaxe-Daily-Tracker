## Incremental operating costs

The new callable adds request/CPU/memory usage per checkout attempt. For N unique products, the proposed successful transaction performs N+6 document reads (profile, existing operation/bill, configuration, sequence, handover, own cashier, products) and 2N+6 writes (products/movements plus bill, state, sequence, handover, cashier, event). Existing checkout performs about N+4 reads and 2N+6 writes; Rules-dependent reads and duplicate SKU reads mean this is a code-path estimate, not measured production billing. Replays need profile+bill reads and no posting writes. Transaction retries may repeat reads; malformed calls, failed calls, logs, network response bytes and eventual build/artifact storage can also contribute usage. No whole-catalogue read or additional listener is needed.

For illustration, 10,000 successful bills add approximately 20,000 document reads before retries and 10,000 Function requests; compute cost depends on measured duration/concurrency/memory and the billing account's remaining allowances. No rupee/month promise is made without those measurements. No min-instance reservation or new service is proposed. Official references: [Firebase pricing](https://firebase.google.com/pricing), [Cloud Run request/compute pricing](https://cloud.google.com/run/pricing), [Firestore operation billing](https://firebase.google.com/docs/firestore/pricing). Existing Blaze status does not imply all incremental usage is free.

### Result and changed files

- Trusted finalizePosCheckout reads authenticated profile/role, catalogue revisions/prices, discount configuration and counter/cashier membership. Monetary arithmetic and discount percentage rounding are recomputed in integer paise. Payments and tender/change are independently validated. A single transaction posts bill, bill state, unique-product deductions/movements, FY sequence, event, cashier requirement and cash/UPI/card totals.
- Operation IDs are existing bill identities, bound to actor UID and normalized intent SHA256 in additive checkout metadata. Replay checks occur before current stock/date/counter checks and return the stored immutable result. Changed intent or another actor cannot reuse the ID. New repeated-SKU intents are consolidated into one bill line, retaining the first line ID, to match mounted POS scan behavior and prevent incompatible restores by existing per-line return/void consumers. Historical bills/lines are not transformed.
- The mounted checkout persists its pending operation and full input in tab session storage, namespaced by Firebase project and actor. It writes this record before dispatch, blocks edits/holding/new finalization during uncertainty, restores pending input after refresh, and focuses the explicit Recover checkout action. Known server rejections allow review/retry; network/internal uncertainty and intent conflicts retain recovery state. No browser posting fallback exists. General unsubmitted cart persistence remains in-memory, as before.
- Rules deny client bill/state creation, sequence creation/update/deletion, sale movement creation/product linkage and bill-finalized event creation. Sale-specific handover/cashier branches were removed. Bills and sale movement evidence cannot be client-deleted. Existing protected join/count/release/reconciliation/closure/refund transitions remain. Generic non-sale stock and orphan refund permissions remain separate unresolved findings.

### Remaining risks, blocked checks and release boundary

1. **Other P0 bugs are unchanged:** fabricated non-sale stock/price sources (AH-SEC-02), orphan refund events (AH-SEC-01) and excessive partial refunds (AH-FIN-01). The checkout handler reads canonical prices but cannot guarantee those records are protected against every other writer. No overall financial-readiness claim; stock-write/refund batches follow Batch 1 review.
2. **Old-client path:** equivalent old direct SDK posting is denied outside and during a count lock; snapshots prove no bill/stock/cash/sequence effect and a held source remains. Actual old installed JavaScript will receive a permission error. This cannot retroactively be turned into a custom message in cached code. The existing UpgradeAnnouncementNotice offers Refresh now; a reviewed coordinated release must provide that announcement and verify old installed clients reload. No announcement or billing/production setting was written here. Native Android upgrade UX remains Blocked/manual; direct-write denial is not native PWA acceptance.
3. **Recovery storage boundary:** tab session storage supports refresh and retained-tab recovery; it does not promise recovery after tab storage is deleted, tab closure or another computer. In that case source lookup through Bills remains necessary. Invalid/unavailable storage blocks new checkout instead of silently discarding a potentially posted intent. No automatic unconfirmed-intent cancellation or new-ID retry exists in the mounted UI. Non-UI callers using the repository adapter must retain/provide their operation ID for retries.
4. **Timed/device cases remain unaccepted:** full shared-counter transition across actual midnight, all actual five-minute expiry paths, staff Cashout window on a physical clock, installed Android PWA upgrade/cache, physical scanner/printer, every phone/modality and all downstream GRN/refund/cheque variants. Controlled clock boundary fixtures, responsive Chromium and receipt HTML are separate evidence.
5. **Environment/architecture limitations:** secondary staff-creation Auth emulator connection remains blocked; broad browser-owned GRN/audit/refund/vendor/Cashout posting, shared subscriptions and the large build chunk warning remain outside Batch 1. Functions engines/dependencies were not upgraded; runtime support deadline remains a separate operations decision.
6. **Deployment safety:** no deployment, commit or push. A later approved release must deploy/verify the endpoint first, coordinate new UI and Rules denial, and review old-client failure/reload behavior. There is no safe rollback to browser posting; retain protected Rules and pause checkout if the trusted endpoint cannot be restored. No production financial mutation is authorized as verification.

All historical production records and collection paths remain unchanged. No index change, independent ledger, loan mutation or unrelated workspace/subscription rewrite was introduced. Tokens, OOB values and synthetic passwords in failure traces were redacted; financial records, screenshots and original failure assertions remain.
