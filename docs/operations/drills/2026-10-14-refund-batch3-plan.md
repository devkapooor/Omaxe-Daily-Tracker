## Money, quantity and date contract

- Remaining quantity = originally billed quantity minus all successfully posted returns, including historical approved returns, regardless of sellable/damaged condition. Rejected legacy requests and unsubmitted UI quotes consume none. Two concurrent staff postings cannot consume the same remaining unit.
- Use original immutable bill line prices and discount, never today's catalogue. Allocate original discount proportionally to gross line value using integer paise: floor each allocation, distribute leftover paise by largest remainder, ties by original line position. Line net totals must sum exactly to the bill's recorded net total. Zero-value bills/lines remain supported; inconsistent totals block rather than being silently normalized.
- For repeated returns of a line, calculate incremental value as floor(lineNet * cumulativeAfter / billedQty) minus floor(lineNet * cumulativeBefore / billedQty). This gives the last unit the remaining paise and prevents repeated rounding leakage. Sum selected line values for the read-only quote; cumulative returned value never exceeds the eligible original bill value.
- Example1:2 units at9000 paise, no discount. Select1 =>9000 refund; after immediate posting remaining1 =>9000; after both posted returns remaining0. Never18000 for a one-unit return.
- Independent rounding fixture: A2x100 plus B1x100, bill discount1 => line nets A199/B100; successive A returns99 then100, B100; total299. These expected numbers are fixture calculations, not application-helper output.
- **New customer returns are Cash even if the original sale used UPI/card/split.** Example: original UPI18000, opening drawer100000, return9000 => UPI collections stay18000, drawer becomes91000, refund cash-out9000, net sales9000. No fabricated UPI/bank reversal. Ledger net cash may be signed; actual available drawer cash, including opening count, must cover the payout.
- Use actual server IST posting date for new cash expense/refund and handover day. Preserve original bill date separately; proposed new return UI displays posting date, not an editable backdated cash payment date. This is a new prospective policy, not a rewrite of old chosen refund dates. Clock crossing midnight requires a fresh confirmation/current counter.
- A zero-valued posted return consumes quantity and creates source evidence/stock restoration where applicable; omit a fictitious cash expense and show No cash paid.

## Trusted server operations and atomic posting

Proposed focused modules: functions/posRefunds.js (handlers), functions/posRefundPolicy.js (allocation/eligibility), exported through functions/index.js; front-end refundRepository.ts/refundRecovery.ts and narrow posRepository adapters. Reuse proven authenticated transaction/idempotency patterns, but keep checkout and stock callable contracts intact.

- Quote callable reads current profile, bill, state and necessary prior proof; returns source revision, quantities, net amounts, source/counter effects and a quote hash. Debounce/coalesce requests, discard stale responses, and bind confirmation to the exact selection/revision. No request/expense/stock writes during quote.
- Post-return callable accepts stable operation ID, source bill/revision, selected quantities, condition, reason and displayed quote/hash. The server derives real actor, receipt reference, Cash method/amount and date; forged/mismatched quote rejects. It reads current source/refund controls/products/handover/cashier/count records and validates role/session, remaining quantity/value and available cash. No owner approval field is accepted as a substitute for this validation.
- One posting transaction creates the source record in the existing approvals path with an additive posted status/posting-mode and separate owner-review status; updates bill state/refund controls; restores aggregated product quantities/revisions once; creates sellable-return movements (none for damaged/temporary lines), canonical event, linked expense, handover effects and original operation result. No stock/payment/expense chunking or browser compensation. Existing bill-return-approved event type may be retained solely for downstream compatibility; new UI/actor metadata must identify staff posting rather than invent owner approval.
- Owner acknowledgement callable binds stable operation to actor/source and updates reviewStatus/reviewedAt/reviewedByUid plus optional review note only; no product/state/refund amount/expense/handover update or additional refund event. Acknowledgement replay recovers original result. Source review is of original posted evidence even if stock/prices have since changed; do not reapply an old return.
- A narrow server action may reject/close an existing pending legacy POS request with no business effects. A legacy return must be explicitly requoted and completed under the new cash policy, optionally linking/closing the old request in the SAME posting transaction. Do not continue the old financial approve route. Legacy void requests can only be closed, never posted.
- Repeated SKU/legacy lines are validated individually by bill line ID and aggregated once per mapped product. Missing product blocks a sellable/void restoration; temporary/unmapped historical lines remain explicitly No stock record, not fabricated inventory. Damaged returns require no quantity restoration. Prices/costs are not changed.
- Server-only per-bill refund controls are additive derived eligibility/recovery records, not another stock ledger. New-write fields contain policy version, allocated net values, consumed quantities/value and source evidence. Historical initialization must reconcile existing approved requests/events/state from filtered, bounded pages and recheck source revision in the posting transaction. No guessed allocations for ambiguous old partial refunds, duplicates or inconsistent amounts; block with source details. Pagination is real cursors/limits, not whole-collection slicing; an unsupported atomic size remains a reported blocker.
- Stable operation ID binds authenticated actor, method and normalized intent. Identical committed replay returns the original result before stale-source/count/counter checks; changed payload/actor rejects. Persist intent before dispatch, including owner acknowledgements; do not clear uncertain results on a pre-lookup auth failure. Missing/corrupt storage fails closed. Recovery is scoped to project/actor/tab; cross-computer/closed-tab recovery is not promised.
